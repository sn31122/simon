## Updating prices through the Scalable MCP (read-only!)

Use only `get_security_chart`, `get_security_quote`, `search_securities`. Never call order, savings-plan, watchlist, price-alert or other write tools. Omit `portfolioId`.

Timeframes (tested 25.–27.09.2026; one ISIN per call, no date parameter): `one_day` = 10-min points of 2 sessions; `seven_days` = 30-min points of ~6 sessions, the last point per day (~20:59 UTC) is the close; `one_month` = 2-hour points (~05:30, 07:29 … 19:29 UTC) of ~1 month, the last point of a day is NOT the close (only the newest day ends with the ~20:59 close point); `three_months` / `six_months` / `year_to_date` = one point per trading day = the daily close (~20:59 UTC; three_months checked equal to `prices_daily.csv` on 67 of 67 days); `one_year` = every 2nd trading day, `max` = monthly – never use those two for daily rows. Ignore `closingReferencePoint`. Since `year_to_date` restarts every January, never delete old rows.

**Subagents (user rules, 27.09.):** Haiku agents **only for price lookups**, always with clear, script-checked instructions and thinking ON. Haiku has no effort setting: start them as agent type `price-fetcher` (model haiku) and begin every fetch prompt with the line `Thinking ON: think step by step before each tool call and before writing each file.` One agent per batch of ≤ 25 ISINs for updates, ≤ 10 for backfills (the hook shrinks each result to one line). **Everything else** delegated (UI, code, review) runs on **Opus 5.5 with effort high or xhigh**: the Agent tool has no effort parameter, so use agent type `dashboard-designer` (Opus, xhigh) or `opus-engineer` (Opus, high), both in `.claude/agents/`. Ask the user whenever something is even slightly unclear.

**Every update follows `UPDATE_PRICES.md`** (skill `update-quotes`; user 25.09.: fetch the intraday prices on every update; user 27.09.: always 30-min for the last seven days and 2-h for the last month):
`python data/update_prices.py --plan` (empties `data/incoming/` except `ytd/`, prints one ready agent prompt per batch) → one `price-fetcher` agent per prompt, all at once: per ISIN `get_security_chart(isin, "seven_days")` and `(isin, "one_month")`; the hook writes `data/incoming/<ISIN>.csv` and `data/incoming/2h/<ISIN>.csv` → `python data/update_prices.py --finish` (check → merge → rebuild → tests → status block in `HANDOFF.md` → report; prints a ready re-fetch prompt for missing/bad ISINs). `--check`, `--dry-run` and the plain run remain available as single steps. The last seven_days point per Berlin date = that day's close / today's latest price (`prices_daily.csv`; only new days, final days are never touched); all seven_days points go to `intraday.csv`, all one_month points to `intraday_2h.csv` (per ISIN and day the newest fetch replaces the stored points, except a shorter cut-off first session). The script marks today as `intraday` before 23:00 Berlin, refuses to finalize an intraday row whose closes were not all refreshed, rebuilds `portfolio-data.js` and deletes the incoming files on success. Cost of a full update (27.09.): 2 Haiku agents × ~55k tokens, 100 calls, ~40 s.

More than 5 weekdays since the last final close: `--plan` adds `three_months` to the prompts and the merge fills the missing closes from it (only new days that seven_days no longer covers). More than ~60 weekdays: `--plan` warns → ask the user (the older closes need `year_to_date` into the legacy `data/incoming.csv`, header `isin,timestamp_utc,price`, only dates after the last final date).

Build warnings: a day-to-day ratio near 2/3/4/5/10/20/50/100/200 flagged `SPLIT` means a split – confirm, divide the whole history of that ISIN before the split date, note it in `HANDOFF.md`. Already adjusted by Scalable: FR0010342592 1:200 on 2026-07-09. Moves > 30 % are flagged for review (known, real ones: Marvell 02.06., D-Wave 21.05., AT&S 15.06., Bloom 30.07.2026; also Halbleiter 3x XS3091657729 −27 % on 05.06.2026 = 3x a −9 % semiconductor day).
`--finish` / `--finish-add` run the tests (below) and rewrite the `data-status` block in `HANDOFF.md`; do not edit that block by hand.

New instrument (only on user instruction; UPDATE_PRICES.md "New instrument"): `search_securities` for the exact ISIN (ask when unclear) → row in `data/instruments.csv` → `python data/update_prices.py --plan-add ISIN[,ISIN]` → one Haiku `price-fetcher` per printed prompt (year_to_date + seven_days + one_month; the hook writes `data/incoming/ytd/`, `data/incoming/`, `data/incoming/2h/`) → `--finish-add ISIN[,ISIN]` (validates, adds the columns, merges closes + 30-min + 2-h points, archives the raw file, rebuilds, tests). From then on the ISIN is in every normal update and in the benchmark search. A new position additionally needs its `positions.csv` row and logo. A chart error → `search_securities` by name, pick the ordinary share / the exact ETF, and ask the user before replacing an ISIN.

## Model conventions

- Backcast: constant share counts from `positions.csv` over the whole history (no transaction history available); price return in EUR, dividends of distributing stocks not included.
- Engine fill rule: forward-fill gaps; before an instrument's first quote it counts flat at its first quote (SpaceX from 2026-06-12).
- Benchmarks are normalized to the portfolio's start value of the selected range. Benchmark cards (built in the UI, not saved): `{weights: {ISIN: %}}`, bought at the first day of the selected range (1T: at the previous close) and then held – buy and hold, no rebalancing (user, 27.09.); only a card with 100 % is drawn. `my_depot` ("Mein Depot", the only locked preset) is the user's real Scalable depot with fixed quantities of 25.09.2026 (update its holdings in `benchmarks.csv` only on user instruction); IE00BF01VY89 has no Scalable quotes 26.01.–09.04.2026 (flat forward-fill).
- Measurement box: the yacht box as in the app; beside it a "Mein Depot" box with "Gleicher Wert" = `equalValueWindow` (the depot's return over the span × the portfolio value at the span start) and "Echt" = `benchmarkRealPl` scaled to the "Mein Depot (€)" field.
- "Startwert" scales all EUR amounts of the selection; % metrics are scale-invariant.
- Chart interval (user, 27.09.; `PFEngine.chartInterval` / `gridFrame`): 1T and 1W 30 min, 1M 2 h, 3M and longer daily; a custom Von/Bis range by its length (≤ 7 calendar days 30 min, ≤ 31 days 2 h, else daily). A finer interval is used only when every session of the range was collected, otherwise it steps down (30 min → 2 h → daily; a note under the chart says so). Main chart, hover, measurement boxes and the drawdown chart follow it; Kennzahlen, Monatsrenditen, tables and sparklines stay daily. Grid rules (`build_data.py`): Berlin slots 07:30–23:00 (30 min) / 07:30…21:30 + 23:00 (2 h), a point goes to the nearest slot (the latest wins), a final day's 23:00 slot is its daily close; per session the previous daily close until the first quote, then forward-fill. A sub-daily chart starts at the daily close of the range start (1T: the previous session as grey context) and benchmark cards are bought there.
